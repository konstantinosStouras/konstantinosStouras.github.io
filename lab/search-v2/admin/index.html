Runs

A run is an immutable parameter set. Once the first participant claims a code every parameter that touches the task is locked; to change anything you clone the run and collect under a new run id. Every event, round and participant row carries its run_id, so two parameter sets can never be silently pooled.

Consequences

Recomputed as you type, so the downstream effect of every setting is visible before anything is launched.

Roster and assignment

Anonymous participant codes only — no names, no e-mail addresses, no free-text identifiers. A student arriving from the class platform enrols with their university student ID, which is the join key between this study’s data and the platform roster.

Generate codes

Codes are assigned to sequences by block randomisation, so the split is exactly half and half rather than a series of coin flips.

Next entrant override

If attrition runs unevenly the crossover balance drifts. This forces the next entrants into the under-filled sequence. A reason is required and is logged.

Live monitor

Counters update live from the participant records. The health checks read the event log, which is heavier — refresh them when you want them.

Validation gate

Runs the adjacency check over the pool, the acceptance filter over every seeded spec, and the balance checks on shape and density. A run cannot open until it passes.

Preview a round spec

Play any spec exactly as a participant would, writing nothing. The testing overlays show the true prizes, the AI’s whole curve and its private anchors, so you can see at a glance whether a seed geometry looks the way it was meant to.

Dry run

Push a scripted bot through a whole session against this run’s specs, in memory, and check that every export column populates. Bot rows are never written anywhere.

Danger zone
